# Проверка абляции при увеличенном стартовом пуле

## Протокол до запуска

Проверяются две новые отложенные конфигурации, сначала `spike`, затем `ramp`. Каждая серия содержит четыре блока с AIMD, полной FQI, аддитивной FQI и полной FQI с фиксированным пулом. В пределах профиля каждый режим занимает каждую позицию один раз. SHA моделей совпадают с [первой абляцией](../postgres-coordination-2026-11-09/README.md). Профили анализируются отдельно. Для каждого используется собственный временный кластер PostgreSQL 17.10 и один JVM-процесс стенда.

Стартовый пул 12 выбран больше начального лимита допуска 10. В свободных режимах пул может меняться в границах 2–16, в варианте с фиксированным пулом обе границы равны 12. Выбор опирается на предыдущую короткую калибровку и на соотношение стартовых ресурсов. Фактическое состояние проверяется по первым пяти секундам измерения. Отдельно фиксируются ресурсы после прогрева и число полных окон со снимками ожидания соединения или полной занятости пула.

В обоих профилях запрос использует 320 000 строк, SLO 150 мс, штатный прогрев 6 с и 20,25 с измерения. В `spike` интенсивность возрастает с 43,2 до 144 запросов/с с 5,4-й до 14,4-й секунды. В `ramp` она линейно растёт с 21,6 примерно до 180 запросов/с. Восстановление считается для `spike` по трём подряд полным окнам после возврата интенсивности, с серверным p95 ≤ 150 мс и goodput ≥ 38,88 запроса/с. Для `ramp` восстановление не определяется.

Основные метрики и парные контрасты те же, что в первой абляции. Описательные 95%-е интервалы Стьюдента строятся по четырём разностям внутри блоков для каждого профиля. Эффект размера стартового пула отдельно не идентифицируется, поскольку между сериями также меняются профили.

## CPU и проверка покрытия

Раз в секунду `ps` снимает накопленное CPU-время дерева JVM-стенда и временного PostgreSQL. JVM включает клиент нагрузки и приложение. PostgreSQL включает postmaster и видимых потомков, в том числе процессы соединений. Измерение использует только интервалы целиком внутри фазы измерения. Среднее число занятых логических ядер вычисляется как суммарное CPU-время, делённое на наблюдавшееся время. Сохраняются доля покрытия, числа появившихся и завершившихся процессов. Аудит требует минимум 80% покрытия фазы в каждом эпизоде.

Выборка процессов может пропустить CPU-время между последним снимком и завершением короткоживущего процесса. Эти метрики описывают работу деревьев стенда и СУБД на общем хосте. Контролируемая CPU-инъекция и замер фоновых процессов в этот протокол не входят.

[Протокол spike](spike.json) и [протокол ramp](ramp.json) фиксируют условия, порядок, метрики и резервирование прежних групп оценки.

[Результаты и исходные трассы](../../raw/postgres-headroom-2026-11-09/README.md) сохранены после завершения обеих серий.

## Воспроизведение

Соберите стенд командой `mvn --offline clean verify` из чистого checkout с JDK 17 и установите [зависимости анализа](../../tools/requirements-ml.txt). Запускайте профили последовательно.

```bash
study=docs/benchmark/analysis/postgres-headroom-2026-11-09
for profile in spike ramp; do
  python3 docs/benchmark/tools/run_postgres_transfer.py "$study/$profile.json" \
    --out "/tmp/iasr-headroom-$profile"
  python3 docs/benchmark/tools/audit_postgres_transfer.py \
    "/tmp/iasr-headroom-$profile" "$study/$profile.json" \
    docs/benchmark/models/fqi-postgres-joint-pilot-2026-11-09/model.json \
    --additive-model docs/benchmark/models/fqi-postgres-additive-2026-11-09/model.json \
    --out "/tmp/iasr-headroom-$profile-analysis.json"
done
```
