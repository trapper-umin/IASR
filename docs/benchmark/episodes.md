# Сохранение экспериментальных эпизодов

Стенд сохраняет каждый завершённый повтор сразу после его выполнения, до выбора представительного прогона для общей таблицы. Новый запуск получает отдельный UUID; указанный вручную `bench.runId` нельзя использовать повторно. Повторная запись существующего эпизода также запрещена.

```
<bench.out>/episodes/<runId>/
  manifest.json
  <scenario>/<mode>/repeat-0001/
    dataset.jsonl
    actuators.csv
    result.json
    metadata.json
```

`metadata.json` записывается последним и служит признаком завершения эпизода. При сбое записи неполный каталог сохраняется для диагностики, а валидатор его отклоняет. Уже завершённые повторы остаются на диске, даже если позднее прервётся весь эксперимент. Незавершённый текущий прогон до возврата из сценария пока не сохраняется потоково.

Metadata содержит версию схемы, идентификаторы запуска и эпизода, номер повтора, `orderSeed`, Git commit и признак изменённого рабочего дерева, начальные ресурсы до/после прогрева, эффективные настройки IASR и guardrails, конфигурацию зависимости, клиента и JVM. Пароль, имя пользователя и JDBC URL не сохраняются. Для точного воспроизведения исходного кода эксперимент следует запускать с зафиксированными изменениями: флаг `dirty` не заменяет сохранённую версию файлов. Число CPU контейнера PostgreSQL и внешние условия машины пока надо фиксировать отдельно.

`orderSeed` управляет начальной перестановкой режимов для каждого сценария. В следующих повторах позиции циклически сдвигаются; за полный цикл каждый режим занимает каждую позицию один раз. Это seed порядка измерений, а не случайности трафика: текущие профили нагрузки детерминированы.

## Временные границы

Сбор журнала продолжается до закрытия Spring-контекста и остановки `ControlEngine`. Поэтому последняя запись с `outcome: null` сохраняется. Она означает отсутствие следующего наблюдения и исключается из обучения, а не получает искусственный нулевой результат.

В `timing` фиксируются начало сбора и прогрева, начало измерения, плановое завершение подачи нагрузки, завершение ожидания ответов и конец сбора журнала. `measurementScheduledEndAt` отделяет заданную нагрузку от дренирования уже отправленных запросов. Окна, пересекающие границу прогрева или завершения нагрузки, не используются как чисто измерительные.

Переходы версии 3 содержат:

- `sequence` — последовательный номер наблюдения внутри сессии контура;
- `timestamp` — момент получения текущего snapshot до принятия решения;
- `stateWindowStartedAt` — предыдущее наблюдение; null для первого окна;
- `outcomeTimestamp` — момент следующего наблюдения; null у последней записи;
- `resourcesBefore` — значения ресурсов до решения;
- `cooldownRemaining` — число блокируемых тиков на момент решения;
- `action`, `intent`, `reasons` — фактические значения после применения, намерение и причины;
- `state`, `outcome` — текущие и следующие метрики с семантикой успешной задержки версии 2.

Не следует восстанавливать начало окна вычитанием настроенного `windowSec`: фактический интервал может отличаться. Остатки cooldown снимаются до enforcement и не продвигают его счётчики.

## Проверка данных

После обычной сборки запуск выглядит так:

```bash
mvn -q install -DskipTests
mvn -pl iasr-benchmark exec:java -Dbench.scenarios=steady,spike -Dbench.modes=fixed,adaptive -Dbench.repeat=2 -Dbench.orderSeed=123 -Dbench.out=/tmp/iasr-data
python3 docs/benchmark/tools/validate_episodes.py /tmp/iasr-data/episodes
```

Валидатор проверяет версии, полноту файлов, количество строк, последовательность наблюдений, конечность чисел, положительность интервалов, связь `outcome_t = state_(t+1)` и ресурсов соседних шагов, а также сохранение последней записи. Он сообщает число полностью измерительных переходов и разнообразие применённых изменений. Интервалы, отличающиеся от заданного окна больше чем на `max(0.1 с, 25%)`, учитываются отдельно и не включаются в число измерительных переходов.

Это проверка целостности и предварительный аудит, а не разрешение на обучение: достаточное покрытие действий, формирование четырёхоконной истории и разделение train/validation/test ещё предстоят. Отсутствующий числовой сигнал (`null`) сохраняется как пропуск, а не заменяется нулём.

`results.csv`, `report.md` и `raw/` по-прежнему содержат один представительный прогон на комбинацию для совместимости. Для новых обучающих данных используются `episodes/`, а не эти представительные файлы. Старые архивы не переписываются в новую схему.
