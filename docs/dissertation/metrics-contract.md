# Семантика метрик для обучаемой политики

Контракт стандартных адаптеров IASR от 8 ноября 2026 года. Новые JSONL-записи имеют `schemaVersion: 2`. Архивы без версии относятся к прежней семантике и не должны автоматически объединяться с новыми данными для обучения.

## Полезная пропускная способность

`goodput_rps` — число успешных бизнес-ответов HTTP 2xx за окно, делённое на фактическую длительность окна. HTTP 3xx, 4xx, 429, 5xx и исключения не являются успешными ответами. В стенде успешен HTTP 200, поскольку его единственный бизнес-эндпоинт возвращает именно этот статус.

Servlet-фильтр записывает каждый бизнес-ответ один раз в `iasr.http.requests`, успешный — дополнительно в `iasr.http.successes`. Отклонение из-за ожидания permit учитывается в `iasr.concurrency.timeouts`, ошибка 5xx или исключение — в `iasr.http.errors`. Инфраструктурные пути обходят фильтр и не меняют эти счётчики.

Провайдер использует собственные бизнес-счётчики при их наличии, даже если `http.server.requests` отсутствует. Фильтр включает их при создании; один лишь `IasrMeterBinder` без HTTP-инструментирования не создаёт пустой источник, скрывающий HTTP-таймеры. При использовании binder вне starter следует вызвать `enableResponseMetrics()` до первого snapshot и затем `recordResponse(status)` один раз на ответ; отдельно вызывать `recordError()` для того же ответа не нужно.

Без бизнес-счётчиков провайдер читает `http.server.requests`:

- если присутствуют теги `status`, goodput вычисляется только по явным 2xx; запросы без status в смешанном наборе не считаются успешными;
- если status отсутствует у всех таймеров, используется приближение `max(0, requests − errors − admission_timeouts)`; другие 4xx и инфраструктурный трафик при этом неотличимы;
- без собственного счётчика ошибок в режиме с HTTP-таймерами ошибки определяются по status 5xx.

`error_rate` и `timeout_rate` делят соответствующие приращения на общее число завершённых запросов того же источника, включая отклонения. Это доли исходов за окно, а не вероятность отказа отдельного входящего запроса: запросы могут завершиться в другом окне, чем поступили. При сбросе счётчиков или смене источника устанавливается новая база, и окно переключения сообщает нулевые скорости.

Первый snapshot использует условную длительность 1 с для совместимости с существующим API. В стенде он относится к прогреву; для обучения первое окно эпизода следует исключать. Начиная со второго snapshot используется монотонное время реестра метрик.

## Задержка и SLO

Для синхронного servlet-запроса стандартный tracker получает две величины одного успешного запроса:

```
total = admission_wait + service
```

`latency_p95_ms`, `latency_p99_ms`, `latency_mean_ms` описывают `total`: от входа в фильтр допуска до завершения цепочки фильтров. Только успешные ответы попадают в распределение. Отклонения и ошибки оцениваются отдельными долями, поэтому нулевая задержка при отсутствии успешных ответов не означает выполнения SLO.

Для каждого запроса сначала складываются его времена, затем вычисляется процентиль по окну. Складывать p95 отдельных составляющих нельзя. Соседние окна независимы, завершившийся запрос целиком попадает в одно окно.

Измерение внутри приложения не включает сеть, очередь клиента и очередь приёма servlet-контейнера. Поэтому клиентский p95 стенда может быть выше. Совпадают успешная популяция и включение ожидания допуска, но это не тождественные точки измерения. Полный жизненный цикл асинхронных servlet-запросов этим фильтром не измеряется.

`service_mean_ms` сохраняет среднее время после получения permit. `admission_wait_mean_ms` измеряет ожидание всех допущенных запросов, включая завершившиеся ошибкой, и может иметь другую популяцию, чем успешный `service_mean_ms`.

`dependency_mean_ms = max(0, service_mean_ms − hikari_acquire_mean_ms)` — оценка остатка, включающая и работу приложения. Она не является точным временем SQL: окна завершений HTTP и получения соединений могут различаться.

Без tracker перцентили недоступны и равны нулю; среднее по HTTP-таймерам и остаток являются приближениями. Если tracker подключён, но успешных ответов нет, провайдер не подменяет их задержку средним по ошибочным ответам.

## Повторение экспериментов

Изменённые goodput и задержка влияют на решения контроллеров. Результаты PostgreSQL от 22 сентября 2026 года остаются результатами старой реализации. Для новых сравнений требуется повторный базовый эксперимент на исправленном коде. Пересчитывать прежние итоговые числа по новым определениям без исходных наблюдений нельзя.

Следующий этап: сохранять версии кода и конфигурации, все повторы и границы прогрева, как предусмотрено в [плане](plan.md).
