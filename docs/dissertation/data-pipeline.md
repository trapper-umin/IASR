# Сбор и подготовка данных для политики

Версия конвейера: 1. В этой итерации реализованы исследующая политика, варьирование условий, четырёхоконные истории, разбиение целых групп и аудит покрытия. Обучение Q-функции и JVM inference ещё не выполняются.

## Исследующая политика

Режим `-Dbench.modes=explore` включается только явно в стенде. Spring Boot Starter по умолчанию продолжает использовать baseline. У исследующей политики есть собственный `policySeed`, который сохраняется в `configuration.exploration`; он отличается от seed порядка режимов.

`JointActionSpace` строит до девяти совместных изменений `{-qL,0,+qL} × {-1,0,+1}`, где `qL=max(1,round(windowSec))`. Действия отбираются по границам ресурсов, ограничению шага, текущему cooldown, SLO-блоку и периоду пула. Затем выполняется обычный guardrail enforcement. Это ограничения параметров, а не гарантия выполнения SLO.

С вероятностью epsilon выбирается равномерное действие из допустимых, включая hold; с вероятностью `1-epsilon` выбирается hold. Поэтому при N кандидатах вероятность hold равна `1-epsilon+epsilon/N`, каждого другого кандидата — `epsilon/N`. Начальное значение epsilon — 0.5. До четырёх активных окон, при отсутствии корректной метрики или активного трафика используется настроенный baseline. Его действия могут не принадлежать сетке и в таком случае исключаются из обучающих меток.

Настройки:

| Параметр | Значение по умолчанию | Назначение |
|---|---:|---|
| `bench.policySeed` | 20261108 | База seed политики; сценарий и повтор детерминированно задают seed эпизода |
| `bench.epsilon` | 0.5 | Вероятность равномерного исследования |
| `bench.poolPeriod` | 5 | Период решений по пулу в тиках |
| `bench.loadScale` | 1 | Множитель интенсивности сценария |
| `bench.durationScale` | 1 | Масштаб длительности и времён всех возмущений |
| `bench.degradedFactor` | 2.4 | Множитель времени зависимости в фазе деградации |

Engine добавляет в наблюдение `control_tick`, `control_window_sec` и `cooldown_remaining.<resource>` до вызова контроллера. Они же попадают в `state`. Номер тика включает прогрев и не выводится из календарного времени или номера строки. Пропуски управляющих шагов исключаются при подготовке истории.

## Матрица условий

[collection-matrix.json](../benchmark/collection-matrix.json) задаёт четыре начальных сочетания ёмкости зависимости, размера пула, конкурентности и интенсивности. Скрипт запускает каждое сочетание в отдельной JVM через Maven, чтобы статические параметры сценариев не переносились между условиями. Предварительно надо собрать текущие артефакты, используемые `exec:java`:

```bash
mvn -q install -DskipTests
python3 docs/benchmark/tools/collect_dataset.py docs/benchmark/collection-matrix.json --out /tmp/iasr-collection --repeat 3 --seed 42 --dry-run
python3 docs/benchmark/tools/collect_dataset.py docs/benchmark/collection-matrix.json --out /tmp/iasr-collection --repeat 3 --seed 42
```

Если Maven отсутствует в PATH, скрипт принимает `--maven /absolute/path/to/mvn`. Команды передаются как argv без shell. Dry-run не запускает стенд. Выходной каталог должен быть новым; при ошибке уже завершённые эпизоды сохраняются, а `collection.json` остаётся незавершённым. Подготовка такого полного каталога отклоняется, пока не собрана корректная коллекция. Автоматическое возобновление пока не реализовано.

Текущая матрица использует синтетическую зависимость. Она подходит для проверки конвейера и предварительного обучения, но не заменяет PostgreSQL-эксперимент из плана. Для реальной БД требуются отдельно зафиксированные настройки контейнера и нагрузки.

## Независимое разбиение

В `configuration.conditions` сохраняются профиль, конфигурация зависимости и клиента, исходные ресурсы, SLO и доступные сведения о среде. Хеш этих условий задаёт группу. Политика, pinned-вариант, повтор, seed, UUID и Git commit не меняют группу; поэтому другая политика на том же объекте не попадает в другой раздел. Внешние условия, которые стенд не измеряет, этим автоматически не контролируются.

```bash
python3 docs/benchmark/tools/prepare_dataset.py /tmp/iasr-collection --out /tmp/iasr-prepared --seed 42 --test-scenarios slow-dependency
```

Нужно не менее трёх различных групп. При указанном `--test-scenarios` все группы выбранных профилей уходят в test. Иначе test получает примерно 20% групп. Validation получает примерно 20%, оставшиеся — train; в каждом разделе должна быть хотя бы одна группа и хотя бы один пригодный пример. Размеры разделов по строкам не выравниваются: целостность групп важнее равного числа строк.

Подготовка требует сохранённой версии исходников. Опция `--allow-dirty` допускается для технического прототипа и явно отражается в manifest; такие данные не становятся воспроизводимым исследовательским результатом. Повторно использовать существующий выходной каталог нельзя.

## Истории и метки

Результат содержит `train.jsonl`, `validation.jsonl`, `test.jsonl`, `manifest.json` и `coverage.json`. Каждый пример включает четыре наблюдённых окна, следующие четыре окна со сдвигом на один шаг, фактическое изменение двух ресурсов и допустимые действия для текущего/следующего наблюдения. Идентификаторы эпизода и группы хранятся отдельно от истории для аудита и не должны становиться признаками модели.

Истории не пересекают эпизоды, прогрев, плановый конец нагрузки, нерегулярные интервалы и пропущенные управляющие шаги. Последняя запись с `outcome: null` не используется как самостоятельный переход. Действие берётся из разницы `action-resourcesBefore`; `intent` не подменяет выполненное действие. Изменения вне заданной сетки или маски исключаются с отдельной причиной в manifest.

Числовые сигналы выбираются явным списком; отсутствующие остаются `null`. Нормализация, заполнение пропусков и вычисление Rref пока не выполняются. На этапе обучения они должны оцениваться исключительно по train. `nextHistory` — целевое следующее наблюдение для FQI, а не часть входа текущего решения.

## Покрытие и ограничения

Отчёт раздельно для train/validation/test содержит частоты действий, пропуски метрик и грубые области состояния: запас SLO, ожидание соединений, загрузку лимита и фазу пула. Для каждого действия видны число возможностей выполнить его, число фактических наблюдений и число независимых эпизодов. Диагностический признак `supported` требует не менее трёх примеров и двух эпизодов; он рассчитывается отдельно в каждом разделе. При обучении использовать для допуска действий можно только информацию train.

Такие области значительно грубее полного пространства признаков. Поэтому даже при выполнении порога `readiness` остаётся `not_established`: достаточность покрытия и эффективность политики ещё надо проверять. Маска допустимости не является обученной моделью, а равномерное исследование не гарантирует посещения всех полезных состояний. Короткие технические прогоны подтверждают связность конвейера, а не качество будущего управления.
