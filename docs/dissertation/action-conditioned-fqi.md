# Q-функция с явным разделением совместных действий

## Проверяемое изменение

Прежний единый ExtraTrees-регрессор получает 208 признаков истории и два признака действия. В проверенных моделях действие часто не влияет на Q в фактически возникающих историях. Следующая попытка проверяет представление Q, не меняя вознаграждение, данные или поддержку.

Для каждой наблюдавшейся **совместной** пары `(dL/qL, dP)` обучается отдельный ExtraTrees-регрессор по 208 признакам состояния. Это не две независимые политики ресурсов: максимум Q выбирает одну пару изменений обоих ресурсов. Маршрутизация по действию задана архитектурой; значения Q обучаются на переходах, без ручного предпочтения увеличивать пул. Маршрутизация сама по себе не доказывает ни влияние действия на систему, ни полезность политики.

Bellman-цель по-прежнему использует максимум предыдущей Q-функции только по допустимым поддержанным действиям следующего состояния. Поддержка согласуется с обучающими переходами до фиксированной точки. Неизвестное продолжение исключается, неизвестное действие не получает фиктивную нулевую оценку.

Редкие совместные действия имеют всего 4–6 переходов. При min leaf 3 некоторые регрессоры останутся константными. Число переходов по каждому действию и случаи с недостаточным количеством для двух листьев сохраняются явно. Разные оценки отдельных регрессоров могут отражать смешение состояний и шум, а не причинный эффект действий; эмпирическая поддержка этого не устраняет.

## Формат и совместимость

Новая модель: `modelVersion: 2`, `algorithm: masked_fqi_action_forests`, `stateFeatureCount: 208`, `actionForests` по нормализованным парам из `{-1,0,1}²`. Каждый лес использует только признаки состояния. На вход переносимого scorer остаются 210 чисел: 208 состояния и два нормализованных действия. Нормализация позволяет использовать qL, зависящий от окна; в support остаются фактические дельты ресурсов.

Модели версии 1 сохраняют прежнее исполнение. JVM loader проверяет соответствие версии алгоритму, отсутствие двусмысленных представлений, нормализованные ключи, наличие леса для каждого поддержанного действия и индексы состояния `<208`. Ограничения: до 9 лесов действий, до 256 деревьев в каждом, суммарно до 200 000 узлов, глубина до 64, файл до 8 MiB. На каждом решении оценивается лес выбранного кандидата; общий `treeCount` в metadata обозначает все хранимые деревья.

Непредставленное действие, дробный нормализованный шаг и повреждённая модель отвергаются. Время inference остаётся кооперативно ограниченным; применение ресурсов выполняет прежний ControlEngine после guardrails. `deploymentAllowed: false` сохраняется.

## Протокол до обучения

- Тот же зафиксированный набор: train 455, validation 120; после согласования поддержки ожидаются 415/106 пригодных переходов. SHA validation не меняется. Test не открывается.
- Два заранее заданных варианта: **pooled/reference** (прежний общий регрессор) и **per-action/experimental** (лес на каждую наблюдавшуюся совместную пару). Это сравнение представлений, без выбора победителя по минимальной Bellman RMSE и без изменения результатов прежнего отбора.
- Общее: 8 итераций, 32 дерева на оценку Q, max depth 6, min leaf 3, max features 1.0, seed 42, gamma 0.95 за секунду, n_jobs 1. Для per-action seed леса равен `(42 + iterationIndex + 1009 × actionIndex) mod 2³²`; действия сортируются по нормализованному ключу.
- Вознаграждение, train-преобразования, поддержка 3 примера / 2 эпизода / RMS 2.0 и состав пригодных переходов одинаковы. Несовпадение этих условий прерывает сравнение. Число параметров различается и сохраняется в отчётах; отдельные леса не являются сравнением при равном объёме модели.
- Сохраняются обе модели, traces, диагностические ошибки и проверки переноса. Сначала проверяются равенство sklearn/JSON/JVM, маски и отказ от неподдержанных действий. Bellman RMSE и количество изменений ресурсов остаются диагностикой, не оценкой производительности.
- После переноса — по одному техническому эпизоду в порядке steady/experimental, steady/reference, spike/reference, spike/experimental. Объект: 8 воркеров / 30 мс, исходный пул 2 (границы 2–12), исходный лимит 20, SLO 150 мс, окно 1 с, pool period 5, бюджет 20 мс. Отдельные JVM, прогрев 6 с, обычные guardrails/fallback. Все действия baseline учитываются отдельно.

Это development-проверка на известных условиях, а не независимый test. Один повтор, различия JIT и времени запуска не позволяют оценивать статистическое превосходство. После просмотра результатов этого протокола модели и параметры не меняются. Новая независимая оценка и траектории с удержанием ресурсов остаются дальнейшими задачами.

## Offline-проверка

На чистом `3c64f21` обе модели обучены и повторены побайтово. Преобразования, поддержка и входы совпали; контрольный pooled сохранил деревья предыдущего reference. У per-action на validation появились 11 предложений увеличить пул, 8 совместных изменений и 2 увеличения лимита; pooled предлагает 6 увеличений пула. У нового варианта выше условная validation Bellman RMSE (1.464599 против 1.214411), поэтому улучшение по offline-диагностике не установлено. Победитель по этой метрике не выбирается.

Оба варианта прошли по 13 JVM-тестов на 74 историях, включая проверку всех обученных действий нового формата. [Артефакты](../benchmark/models/fqi-action-conditioned-2026-11-08/README.md) и [план технических эпизодов](../benchmark/models/fqi-action-conditioned-2026-11-08/technical-check-plan.json) сохранены до запуска контура. Архитектурное разделение и большее число предложений ещё не подтверждают полезность действий.
