# Следующая итерация данных совместной политики

## Диагноз первого набора

Новая диагностика `audit_joint_learning.py` пересчитывает поддержку только на train и анализирует чувствительность Q на train/validation. Файл test не открывается. На первом наборе из 260 train-переходов фильтр оставил 237: 14 увеличений пула, 8 уменьшений пула и **ни одного одновременного изменения L и P**. Все 7 исходных совместных изменений исключены из-за поддержки/продолжения. Проверка наличия совместных действий до фильтра не гарантировала их наличия в фактическом обучении.

В первом лесу нет разбиений по действию пула. При фиксированном действии над лимитом все сравнимые поддержанные изменения пула имеют одинаковый Q. Это наблюдаемое свойство текущей модели; оно не доказывает, что причина только в объёме данных или что увеличение выборки автоматически поможет.

Сохранён [аудит](../benchmark/analysis/joint-support-2026-11-08/original-model-audit.json). Описания исходов через 1, 3 и 5 окон учитывают разрывы, повторные изменения пула и изменения лимита в промежутке. Они являются описательной статистикой наблюдавшихся траекторий, а не причинной оценкой действий.

## Изменение реализации

Тренер теперь проверяет необходимое покрытие **после** согласования поддержки: должны остаться рост и уменьшение пула и хотя бы одно одновременное изменение обоих ресурсов. Это необходимый минимум, не достаточность данных и не доказательство обученного согласования. Диагностическое воспроизведение старой модели требует явного `--allow-incomplete-joint-support`; экспорт сохраняет отрицательный статус покрытия и `deploymentAllowed: false`.

Режим `explore-balanced` выбирает наименее часто выбранное допустимое действие в грубой области: диапазон p95/SLO, наличие ожидания пула, занятость лимита и фаза пула. Равные счётчики разрешаются независимым seeded RNG. SLO, cooldown и границы проверяются заново на каждом тике. Счётчики относятся к выбранным предложениям внутри эпизода; фактическое покрытие проверяется по применённым действиям после guardrails. Балансирование не гарантирует посещение всех состояний, достаточность поддержки или отсутствие смешения эффектов.

`prepare_dataset.py --development-only --validation-scenarios spike` сохраняет только train/validation; все повторы профилей остаются вместе. `train_fqi.py --development-only` не открывает test и помечает его как неоценённый. Такой результат предназначен для разработки, а не для окончательной проверки гипотезы.

## Зафиксированный протокол пилота

Протокол фиксируется до сбора новых эпизодов и до оценки новой модели:

- Только синтетический объект: 8 воркеров, 30 мс обслуживания, исходный пул **2**, диапазон пула **2–12**, исходный лимит **20**, SLO 150 мс, окно 1 с и pool period 5. Остальные настройки стенда остаются стандартными.
- Режим `explore-balanced`, epsilon 1, policy seed **20261109**, order seed 42; по **3 повтора** полных профилей `steady`, `ramp`, `spike`.
- `steady` и `ramp` целиком относятся к train; `spike` целиком к validation. Нового test в пилоте нет. Старый test не используется для выбора модели и недостаточен для окончательной новой оценки.
- Пороги поддержки остаются 3 примера / 2 эпизода / RMS 2.0. Преобразования — train only; первая попытка обучения сохраняет 8 итераций / 32 дерева / глубину 6 / leaf 3 / seed 42 / gamma 0.95. Параметры не выбираются по test.
- При недостатке покрытия после фильтра новый совместный артефакт не экспортируется. При достаточном минимуме оцениваются чувствительность по действиям, предложения и условная Bellman-диагностика validation. Они не считаются оценкой производительности политики.
- Переход к новому независимому эксперименту допускается после проверки переноса и поведения модели. Если пул снова игнорируется, результат сохраняется без принудительного добавления обученной политике ручного правила изменения пула.

Сбор использует обычный `BenchmarkRunner` с `-Dbench.modes=explore-balanced -Dbench.scenarios=steady,ramp,spike -Dbench.repeat=3 -Dbench.epsilon=1 -Dbench.policySeed=20261109 -Dbench.orderSeed=42 -Dbench.db.workers=8 -Dbench.db.serviceMs=30 -Dbench.poolSize=2 -Dbench.poolMin=2 -Dbench.poolMax=12 -Dbench.initialLimit=20`. Каждый эпизод сохраняет собственные конфигурацию и provenance; исходники коммитятся перед запуском.

```bash
python3 docs/benchmark/tools/prepare_dataset.py /tmp/iasr-balanced-pilot \
  --out /tmp/iasr-balanced-prepared --development-only --validation-scenarios spike
python3 docs/benchmark/tools/audit_joint_learning.py /tmp/iasr-balanced-prepared \
  --out /tmp/iasr-balanced-audit.json
python3 docs/benchmark/tools/train_fqi.py /tmp/iasr-balanced-prepared \
  --development-only --out /tmp/iasr-balanced-model
```

## Результат пилота

[Данные](../benchmark/raw/balanced-pilot-2026-11-08/README.md) дали 195 train и 120 validation-примеров. После фильтра осталось 166 переходов, включая четыре совместных изменения, но ни одного увеличения лимита. [Фиксированная development-модель](../benchmark/models/fqi-balanced-pilot-2026-11-08/README.md) впервые использует действие пула в одном узле и предлагает восемь изменений пула на train, однако на validation изменений пула нет. Узел пула имеет поддержанные кандидаты по обе стороны порога в семи train-историях и ни в одной validation-истории.

Новые JVM-тесты на 81 истории прошли; модель воспроизвелась побайтово. В двух технических замкнутых эпизодах все 54 решения и 28 support fallback совпали с Python. Изменений пула обученной моделью в контуре нет; изменение пула baseline не считается достижением обученного согласования. Эта итерация улучшила диагностику и необходимое покрытие, но не закрыла критерий этапа 4.

Продолжение: сохранить известные train-траектории при расширении набора, добавить состояния с безопасным увеличением лимита и сопоставимые действия пула; проверить представление действий и задержанные последствия. Затем настройка на validation и новый независимый эксперимент. Модель и пороги в этом пилоте не перенастраивались по результатам его JVM-прогона.
