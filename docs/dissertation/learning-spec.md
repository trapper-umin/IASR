# Спецификация обучаемой политики

Версия проекта постановки: 1, 8 ноября 2026 года. Это план проверяемого метода; реализация обучения и его эффективность пока не установлены.

## Гипотеза и объект управления

Совместная политика выбора предела конкурентности L и размера пула P может улучшить сочетание полезной пропускной способности, задержки и отказов относительно настроенных правил и независимых политик. Проверяется вклад обучения и совместного выбора, а не только добавления второго регулируемого ресурса. Отрицательный результат допустим.

Наблюдения частичны: истинная ёмкость БД неизвестна контроллеру. История измерений используется как приближённое состояние; марковское свойство и устойчивость этим не доказываются.

## Наблюдение

На шаге k политика получает последние четыре полностью наблюдённых окна и текущее состояние ресурсов:

| Группа | Признаки |
|---|---|
| Задержка | p95/SLO, p99/SLO, mean/SLO, service_mean/SLO |
| Исходы | goodput/Rref, error_rate, timeout_rate |
| Конкурентность | inflight/L, queue_length/L, admission_wait_mean/SLO |
| Пул | active/P, idle/P, pending/P, acquire_mean/SLO |
| Контекст | CPU, GC p95/SLO, фактическая длительность окна |
| Управление | L и P относительно заданных диапазонов, остатки cooldown, фаза медленного контура |

Rref — один фиксированный масштаб goodput, вычисленный только по train и сохранённый вместе с моделью; это не истинная ёмкость зависимости. Размеры ресурсов берутся из `resourcesBefore`, а не из действия, выбранного после наблюдения. Будущий `outcome`, название сценария, режим, номер повтора, истинные параметры синтетической зависимости и время до возмущения в признаки не входят.

Отсутствующие и нечисловые значения получают явные маски; статистики заполнения определяются только по train. Первое окно без известной длительности и окна пересечения границ прогрева исключаются. До накопления четырёх допустимых окон используется baseline. При смене эпизода история очищается.

## Совместные действия и ограничения

Первый вариант имеет до девяти совместных действий `(dL, dP)` из `{-qL, 0, +qL} × {-1, 0, +1}`. qL равен `max(1, round(1 × windowSec))`, то есть номинально одна единица конкурентности в секунду. Пул допускает изменение раз в пять тиков; на остальных тиках dP = 0. Фаза отсчитывается от начала сессии, включая прогрев, и должна быть доступна при обучении и inference.

Сначала отбрасываются заведомо недопустимые кандидаты по текущим диапазонам, cooldown и SLO-блоку. Окончательное применение выполняет существующий слой guardrails. В датасете хранятся ресурсы до действия, намерение, причины вмешательства и фактические ресурсы после применения. Действие для модели — фактическое изменение ресурсов. Разные намерения, приведшие к одному применённому действию, объединяются; запрещённое намерение не размечается как выполненное.

Параметры действий и периода пула — часть конфигурации эксперимента. Архивы старых контроллеров могут содержать другие шаги; их нельзя автоматически считать покрытием девяти выбранных действий. Если покрытия недостаточно, собирается новая выборка.

## Критерий обучения

Проект начального вознаграждения за результат следующего окна:

```
r = goodput_next / Rref
    - 2 × min(10, max(0, p95_next / SLO - 1))
    - timeout_rate_next - 2 × error_rate_next
    - 0.05 × (abs(dL)/rangeL + abs(dP)/rangeP)
```

Для закреплённого ресурса его слагаемое изменения равно нулю. Отсутствие успешных ответов даёт нулевое слагаемое goodput, но не стирает штрафы ошибок и отклонений. При отсутствии событий окно не используется как доказательство выполнения SLO. Это штраф за превышение p95, а не доля отдельных запросов, нарушивших SLO.

Числа 2, 1 и 0.05 — исходные коэффициенты проекта эксперимента, а не доказанный оптимум. Они фиксируются до теста и исследуются на validation. Итоговая оценка проводится по исходным показателям отдельно, поскольку скалярное вознаграждение может скрыть нежелательный размен задержки на отказы.

## Метод обучения

Первый кандидат — offline Fitted Q Iteration (FQI) с ансамблем регрессионных деревьев. Метод сводит обучение по переходам `(s, a, r, s_next)` к последовательности задач регрессии Q-функции; первоисточник: Ernst, Geurts, Wehenkel, [Tree-Based Batch Mode Reinforcement Learning, JMLR, 2005](https://jmlr.org/papers/v6/ernst05a.html).

Причины выбора для первого прототипа: небольшое дискретное пространство действий, уже предусмотренный сбор переходов и возможность отделить offline обучение от JVM inference. Это проектное решение для IASR, а не утверждение о превосходстве FQI над другими методами.

```
Q_0(s,a) = 0
target_j = r_j + gamma_j × max_b Q_(i-1)(s_next_j,b)
gamma_j = 0.95 ** elapsedSeconds_j
Q_i = regression((s_j,a_j), target_j)
```

Максимум берётся только по допустимым и достаточно представленным действиям. Правило достаточного покрытия определяется на train/validation до теста; до его реализации эксплуатация обученной политики не разрешается программной конфигурацией по умолчанию. Одних guardrails недостаточно, чтобы устранить ошибку оценки незнакомых действий. Если подходящего кандидата нет, применяется baseline.

Окончание файла и `outcome: null` означают цензурирование, а не терминальное состояние физической системы: такой переход не получает выдуманного нулевого будущего. Переходы через завершение эпизода не строятся. Число итераций, структура деревьев, покрытие и коэффициенты выбираются по validation.

Для переноса в JVM планируется сохранять деревья и порядок признаков в проверяемом формате с тестом равенства Python/JVM inference. Импорт произвольных pickle-файлов в приложение не требуется. До экспорта модель должна пройти offline проверки и новый стендовый эксперимент.

## Сбор и разделение данных

Каждый повтор — отдельный эпизод с версией кода, конфигурацией, исходными ресурсами и границами прогрева/измерения. `orderSeed` задаёт только порядок режимов; существующая нагрузка детерминирована, seed исследующей политики будет отдельным полем после её реализации.

Окно состояния и окно результата должны целиком лежать в измерительной фазе. Границы определяются по `stateWindowStartedAt`, `timestamp`, `outcomeTimestamp` и временам из metadata. Настроенное `windowSec` не заменяет фактически наблюдённые интервалы. Последняя незавершённая запись сохраняется для аудита и исключается из обучающих переходов.

Train/validation/test разделяются по группам полных запусков. Все политики и повторы одной комбинации условий и профиля нагрузки остаются в одном разделе. Отдельный тест содержит новые профили и параметры зависимости; случайное разделение соседних строк недопустимо.

## Проверка гипотезы

Сравниваются fixed, текущий AIMD, реализация Gradient в стенде, обученная одноресурсная политика, две независимые обученные политики и совместная политика. Gradient в проекте — адаптация механизма к оконному SPI, а не оригинальная библиотека Netflix; это ограничение сохраняется в тексте результатов.

Проверяются нормальная нагрузка, пики, рост, деградация, восстановление, достаточный стартовый пул и новые сочетания условий. Основные показатели: goodput, клиентские p95/p99, ошибки, отклонения, превышения SLO, время восстановления и изменения ресурсов. Порядок режимов балансируется, отрицательный контроль сохраняется. Интервалы оцениваются для различий между режимами; отсутствие пересечения двух отдельных интервалов не заменяет анализ различия.

Новый сравнительный PostgreSQL-прогон обязателен: данные до изменения метрик не являются новой базовой линией. Формальная устойчивость связанной обучаемой системы не заявляется. Проверяемые ограничения guardrails уточнены в [постановке базового контура](../paper/problem-statement.md).

## Состояние реализации

В этой итерации реализуются поля переходов, сохранение всех эпизодов и проверка их целостности. Исследующая политика, подготовка train/validation/test, обучение FQI и JVM inference остаются следующими задачами; наличие спецификации не означает их готовности.
