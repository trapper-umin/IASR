## Что подтверждено данными

Эти выводы определяют формулировку новизны и положений на защиту. Тема описывает направление исследования, а не доказанный заранее тезис.

1. **Координация второго ресурса полезна при дефиците пула.** Полная FQI снизила p95 относительно той же модели с пулом 5 во всех четырёх блоках: −156,75 мс [−300,20 … −13,30] ([абляция координации](../benchmark/raw/postgres-coordination-2026-11-09/README.md)). Ранее для правил AIMD получено +6,4…+17,7% goodput от разрешения управлять пулом ([findings](../benchmark/findings.md)).
2. **При достаточном стартовом пуле выигрыша не обнаружено.** При пуле 12 все парные интервалы по goodput и p95 включают ноль ([headroom](../benchmark/raw/postgres-headroom-2026-11-09/README.md)).
3. **Обучаемая политика не превзошла настроенный AIMD.** Первое отложенное сравнение: −2,70 rps и +251,5 мс p95, интервалы включают ноль; fallback по поддержке в 128 из 176 окон ([transfer](../benchmark/raw/postgres-transfer-2026-11-09/README.md)). Без CPU-нагрузки goodput FQI ниже во всех четырёх блоках ([CPU](../benchmark/raw/postgres-cpu-pressure-2026-11-09/README.md)).
4. **Полная совместная Q-функция не отличима от аддитивной** по goodput и p95, хотя применяет больше совместных изменений (7 против 1; 14 против 3).
5. **Безопасное встраивание работает инженерно.** Guardrails, маска действий, проверка эмпирической поддержки, бюджет inference и baseline fallback; побайтовая воспроизводимость моделей; совпадение решений Python/JVM; inference ≤ 5,5 мс.

Не заявляется: превосходство обученной политики над AIMD, формальная устойчивость, перенос на другие объекты.

## Этапы 1–4 (завершены)

- **Этап 1.** Goodput без отклонённых запросов, ожидание допуска в задержке SLO, отдельное время обслуживания, регрессионные тесты, `schemaVersion: 2`. Подробно — [контракт метрик](metrics-contract.md).
- **Этап 2.** [Спецификация обучения](learning-spec.md): четырёхоконное наблюдение, 9 совместных действий `(dL, dP)`, вознаграждение, offline FQI, разделение по группам условий. Устойчивость не заявляется.
- **Этап 3.** Эпизоды с конфигурацией, seed и версией кода; исследующие политики `explore` и `explore-balanced`; валидатор, аудит покрытия, разбиение по группам. Подробно — [конвейер данных](data-pipeline.md), [расширение train](joint-data-iteration.md), [сохранение train](retained-train-iteration.md). Достаточность данных установлена только косвенно — по доле поддержанных состояний validation (157/160 после PostgreSQL-развития).
- **Этап 4.** [FQI-прототип](fqi-prototype.md), [per-action Q](action-conditioned-fqi.md), [JVM runtime](jvm-policy.md). Сохранённая модель управляет обоими ресурсами в стенде, включая совместные изменения.

## Этап 5. Проверка гипотезы — завершение

Выполнено: сравнение fixed / AIMD / Gradient / FQI на отложенной конфигурации; абляция координации (AIMD, полная FQI, аддитивная FQI, FQI с фиксированным пулом); две серии с пулом 12 и CPU-трассами; эксперимент с CPU-нагрузкой; парные интервалы и архив всех эпизодов.

Оставшиеся шаги:

- [ ] **Разобрать дрейф между блоками.** В CPU-эксперименте p95 обеих политик рос в блоках 1–2 и падал в 3–4. До новых прогонов проверить источник (прогрев хоста, термика, фоновые процессы, состояние Docker) и описать как угрозу валидности.
- [ ] **Оценить мощность.** По дисперсии парных разностей уже проведённых серий оценить число блоков, нужное для обнаружения практически значимого эффекта (например, 10% p95 или 3 rps goodput, порог различимости стенда ~3%).
- [ ] **Финальная подтверждающая проверка — одна, заранее зафиксированная.** Цель: подтвердить или опровергнуть единственный положительный результат (координация при дефиците пула) на новом профиле. Режимы: AIMD, полная FQI, полная FQI с фиксированным пулом. Число блоков — по оценке мощности; основная метрика и поправка на множественность фиксируются до запуска; модель не переобучается.
- [ ] **Привести спецификацию к фактическому набору сравнений.** В [learning-spec](learning-spec.md) обещаны одноресурсная обученная политика и две независимые обученные политики; фактически использованы FQI с фиксированным пулом и аддитивная FQI. Обосновать замену или явно указать как ограничение.
- [ ] **Сводная таблица результатов** всех серий PostgreSQL с долей решений модели, fallback и числом совместных изменений — исходный материал для главы 4.

Переносится в «Ограничения и дальнейшую работу» (не выполняется до защиты, если не останется времени после этапа 6): фиксированная CPU-квота, перенос на другой объект (другое приложение или СУБД), формальный анализ устойчивости, online-дообучение.

**Критерий завершения и заморозка.** После финальной проверки эксперименты прекращаются. Новые прогоны допускаются только для исправления ошибки в уже полученных данных. Каждый вывод в тексте ссылается на сохранённый эпизод или отчёт.

### Проект положений на защиту

Уточняется после финальной проверки; формулируется только по подтверждённому.

1. Архитектура согласованного управления несколькими мягкими ресурсами со встраиванием обучаемой политики через общий слой ограничений, проверку эмпирической поддержки и переход к базовому регулятору.
2. Постановка задачи offline-обучения совместной политики управления пределом конкурентности и пулом соединений и методика воспроизводимой проверки с разделением данных по группам условий.
3. Экспериментально установленные условия полезности согласованного управления: выигрыш при дефиците пула и его отсутствие при достаточном пуле; обучаемая политика на собранных данных не превосходит настроенный AIMD.
