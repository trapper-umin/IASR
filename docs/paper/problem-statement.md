# Формальная постановка задачи и свойства контура

Рабочий документ для статьи. Здесь задача записана формально, закон управления выписан ровно в том виде, в каком он реализован в `BaselineController`, и отдельно разобрано, какие свойства контура **доказуемы**, какие **обоснованы измерением**, а какие **не установлены**. Последнее разделение существеннее первых двух: рецензент проверяет именно его.

---

## 1. Объект и предмет

**Объект** — серверное приложение на JVM, обслуживающее поток запросов и опирающееся на внешнюю зависимость ограниченной ёмкости.

**Мягкий ресурс** — параметр конфигурации, определяющий пропускную способность или степень параллелизма, который технически допускает изменение во время работы процесса, но на практике задаётся при запуске и далее не меняется: предел одновременно обслуживаемых запросов, размер пула соединений, размеры пулов потоков, глубины очередей, тайм-ауты.

**Предмет** — правила согласованного изменения нескольких таких ресурсов по обратной связи без перезапуска приложения.

## 2. Формальная постановка

### 2.1. Управление и наблюдение

Время дискретно: `k = 0, 1, 2, …` с шагом `Δt` (окно управления).

Вектор управления объединяет `n` мягких ресурсов:

```
u(k) = (u₁(k), …, uₙ(k)),   uᵢ(k) ∈ [uᵢᵐⁱⁿ, uᵢᵐᵃˣ] ⊂ ℕ
```

В реализации `n = 2`: `u₁ = L` — предел конкурентности, `u₂ = P` — максимальный размер пула соединений.

Вектор наблюдения:

```
y(k) = ( ℓ(k), g(k), τ(k), e(k), n(k), q(k), π(k), ι(k), a(k) )
```

где `ℓ` — p95 латентности за окно, `g` — goodput, `τ` — доля клиентских тайм-аутов, `e` — доля ошибок, `n` — число запросов в обработке, `q` — длина очереди за permit, `π` — число потоков, ждущих соединения, `ι` — число простаивающих соединений, `a` — p95 времени получения соединения.

### 2.2. Возмущение и почему задача нетривиальна

Внешние условия — интенсивность входного потока `λ(t)` и ёмкость зависимости `C(t)` — экзогенны и меняются во времени. **`C(t)` ненаблюдаема напрямую**: приложение видит латентность, а не ёмкость.

Калибровка (`docs/benchmark/methodology.md`) даёт структурный факт, на котором держится вся постановка. Пропускная способность зависимости как функция конкурентности `c` **унимодальна**:

```
T_dep(c) растёт при c < c*,  достигает максимума при c = c*,  убывает при c > c*
```

причём измеренный `c*` совпал с числом ядер, выданных контейнеру (2 ядра → `c* = 2`, 6 ядер → `c* = 6`).

Отсюда следствие, ради которого задача вообще существует: **целевая функция не монотонна по `u`**, поэтому стратегия «выставить максимум» не оптимальна, а задача является задачей оптимизации, а не максимизации. Если бы `T_dep` выходила на плато, переразмеренность была бы бесплатной, любой статический максимум был бы решением, и никакой контур не был бы нужен.

### 2.3. Критерий

Требуется найти политику `u(k) = π(y(0..k))`, доставляющую

```
максимум   G = (1/K) · Σₖ g(k)                        — пропускная способность
при        ℓ(k) ≤ S                                   — SLO на хвост латентности
           uᵢ(k) ∈ [uᵢᵐⁱⁿ, uᵢᵐᵃˣ]                      — допустимый диапазон ресурса
```

Ограничение по SLO при перегрузке невыполнимо: если `λ(t)` превосходит достижимую ёмкость, никакая политика не удержит `ℓ ≤ S` для всех запросов. Поэтому фактически решается смягчённая задача — минимизировать долю нарушений SLO и долю сброшенных запросов при максимуме пропускной способности; **три критерия конфликтуют, и в отчёте они приводятся совместно, а не сворачиваются в один показатель.**

### 2.4. Связь наблюдаемых величин

Закон Литтла `L = λW` в стационаре даёт целевую конкурентность, при которой латентность равна SLO:

```
L* = λ_offered · S,     λ_offered = g / (1 − τ)
```

Предложенная интенсивность берётся вместо достигнутой намеренно: достигнутая уже подавлена тем, что лимитер отбрасывает, и оценка лимита по ней означала бы оценку лимита по величине, которую сам лимит и произвёл.

**Ограничение** должно быть названо в статье прямо: закон Литтла верен в стационаре, а контур работает преимущественно на переходных режимах, поэтому `L*` используется как ориентир и потолок роста, а не как уставка.

## 3. Закон управления

Выписан в соответствии с реализацией. Параметры: `S` — SLO, `c_f` — доля SLO, ниже которой состояние считается комфортным (0.7), `γ` — нижняя граница градиента (0.9), `δ⁺` — шаг аддитивного роста (1), `β` — множитель геометрического снижения (0.85), `g_u` — порог востребованности (0.9), `h` — запас для цели по Литтлу.

### 3.1. Предикаты

```
V(k)  ≡  ℓ(k) > S                              — нарушение SLO
C(k)  ≡  0 < ℓ(k) < c_f · S                    — комфортное состояние
B(k)  ≡  q(k) > 0  ∨  n(k) ≥ g_u · L(k)        — лимит является связывающим
T(k)  =  h · λ_offered(k) · S                  — цель по закону Литтла
```

### 3.2. Конкурентность

```
если V(k) ∨ (τ растёт) ∨ (e растёт):
        L(k+1) = max(1, ⌊L(k) · max(γ, min(1, S / ℓ(k)))⌋)      при V(k), γ > 0
        L(k+1) = max(1, ⌊L(k) · β⌋)                             иначе
        L(k+1) = min(L(k+1), T(k))                              при V(k), T(k) > 0

иначе если C(k) ∧ (e, τ малы):
        L(k+1) = L(k)                                            если ¬B(k)
        L(k+1) = L(k)                                            если L(k) + δ⁺ > T(k) > 0
        L(k+1) = L(k) + δ⁺                                       иначе

иначе:  L(k+1) = L(k)
```

### 3.3. Пул соединений

```
если π(k) > θ_π ∧ a(k) > θ_a:                    P(k+1) = P(k) + s     — дефицит соединений
иначе если пул избыточен 10 тактов подряд:        P(k+1) = P(k) − s     — простаивающие соединения
иначе если пул только что вырос ∧ V(k) ∧ ℓ(k) > 1.1·ℓ(k−1):
                                                  P(k+1) = P(k) − s     — откат ухудшившего решения
иначе:                                            P(k+1) = P(k)
```

где «пул избыточен» ≡ `π(k) ≤ θ_π ∧ ι(k) ≥ θ_ι`. Признак избыточности — **простаивающие соединения**, а не отсутствие очереди: пул правильного размера очереди тоже не имеет, и снижение по отсутствию очереди отбирало бы запас именно в спокойные периоды, предшествующие возмущению.

### 3.4. Guardrails

Решение контроллера не применяется напрямую. Слой ограничений выполняет последовательно: **cooldown** (не чаще одного изменения в `c` тактов) → **блокировка при нарушении SLO** для действий, способных его усугубить → **ограничение шага** `|Δuᵢ| ≤ Δᵢᵐᵃˣ` → **абсолютное ограничение** `uᵢ ∈ [uᵢᵐⁱⁿ, uᵢᵐᵃˣ]`.

## 4. Доказуемые свойства

Первые два свойства относятся к настроенному слою guardrails, третье — только к отдельной ветви baseline. Предполагаются допустимые исходные значения ресурсов, неизменная конфигурация ограничений, отсутствие внешнего изменения актюаторов и корректная реализация их API. Если для ресурса нет guardrail, эти ограничения для него не установлены. Ограничения параметров не доказывают устойчивость приложения и не гарантируют SLO.

**Свойство 1 (ограниченность).** Для всех `k` и всех `i`: `uᵢ(k) ∈ [uᵢᵐⁱⁿ, uᵢᵐᵃˣ]`. Следует непосредственно из абсолютного ограничения, применяемого последним.

**Свойство 2 (ограниченность скорости изменения).** Пусть `Δᵢ = max(maxStepᵢ, effectiveMaxStepDownᵢ)`. В реализации после разрешённого изменения пропускаются `c` следующих тиков, поэтому минимальный интервал между разрешёнными изменениями равен `c+1`, включая случай `c=0`. На любых `m` последовательных переходах:

```
|uᵢ(k+m) − uᵢ(k)| ≤ ⌈m / (c+1)⌉ · Δᵢ
```

Это ограничивает скорость изменения параметра, но допускает колебания в пределах ограничений. Отказ применения может сделать управление реже; guardrails учитывают разрешённое изменение до вызова актюатора.

**Свойство 3 (округление градиентного снижения).** Только для сырого решения ветви градиентного снижения, без дополнительного ограничения целью по Литтлу: `L_raw(k+1) ≥ max(1, floor(γ · L(k)))`. Более сильное неравенство `L_raw(k+1) ≥ γ · L(k)` неверно: при `L=11`, `γ=0.9` получается 9 вместо нижней границы 9.9. При включении цели по Литтлу или ветви ошибок эта граница не распространяется на результат. Универсальную границу фактического снижения задаёт `maxStepDown`, а прежняя оценка времени уменьшения вдвое через логарифм без учёта округления неприменима.

## 5. Устойчивость: аргументы и измерения

Формального доказательства устойчивости нет (см. раздел 6). Ниже — аргументы, каждый из которых либо опирается на известный результат, либо подтверждён замером.

### 5.1. Наследование AIMD

Закон управления конкурентностью асимметричен: рост аддитивный, снижение мультипликативное. Chiu и Jain показали, что именно эта асимметрия обеспечивает сходимость к эффективному и справедливому распределению канала между потоками, тогда как схемы AIAD и MIMD к справедливому распределению не сходятся. Наш контур наследует эту форму; сам же результат доказан для нескольких потоков, делящих общий ресурс, и на одиночный контур переносится как эвристическое обоснование, а не как доказательство.

### 5.2. Снижение пропорционально ошибке и самозатухает

Множитель `min(1, S/ℓ)` делает непрерывную коррекцию зависимой от величины нарушения, а не фиксированной. При `ℓ → S⁺` множитель стремится к 1. Однако после округления вниз даже сколь угодно малое положительное нарушение может уменьшить целый лимит на единицу. Следовательно, исчезновение непрерывной ошибки не доказывает исчезновения фактического изменения или отсутствия перерегулирования.

Это подтверждено замером: порог 0.9, разрешающий срезать не более 10% за такт, оказался **лучше** геометрического ×0.85 с его пятнадцатью процентами — то есть выигрывает пропорциональность, а не агрессивность.

### 5.3. Почему агрессивное снижение разрушает рабочую точку

Пусть `γ = 0.5` и `ℓ = 2S`. Тогда лимит делится пополам **каждый такт**, тогда как рост ограничен `δ⁺ = 1` за такт. Восстановление после среза на `Δ` требует `Δ/δ⁺` тактов. При `L ≈ 40` один такт снижения отбирает 20 единиц, на возврат которых нужно 20 тактов — контур проводит бо́льшую часть времени ниже эффективной точки, восстанавливаясь.

Измерение согласуется: при `γ = 0.5` пропускная способность падает, а сброс растёт по сравнению с `γ = 0.9` (таблица порогов в `findings.md`). **Правило выбора `γ`:** типичное нарушение должно вызывать срез, восстановимый за время, меньшее характерной длительности возмущения.

### 5.4. Гейт востребованности как защита от насыщения интегратора

Без условия `B(k)` аддитивный рост не имеет понятия «достаточно»: он повышает лимит на каждом такте с комфортной латентностью, независимо от того, ждёт ли кто-нибудь permit. Сервис, спокойно работающий при семи одновременных запросах, доводит лимит до потолка и встречает возмущение без запаса управления — **лимит максимален ровно тогда, когда защита нужнее всего.**

Это в точности насыщение интегратора (integrator windup), а предикат `B(k)` — стандартная защита от него: интегрирование продолжается только пока управляющее воздействие реально связывает. Измеренный эффект — улучшение хвоста во всех стрессовых сценариях при неизменной пропускной способности.

### 5.5. Разделение контуров по времени

Два регулятора читают один и тот же сигнал латентности и действуют на одну систему; при равных частотах они образуют связанную пару, способную реагировать друг на друга. Лимит решается каждый такт, пул — раз в `N` тактов (по умолчанию 5).

Обоснование не вкусовое, а физическое: **изменение допуска обратимо в пределах такта и действует немедленно, тогда как изменение пула требует открытия соединений, и его влияние на латентность проявляется через несколько окон.** Решать по пулу чаще, чем наблюдается его собственный эффект, значит реагировать на переходный процесс предыдущего изменения, а не на его результат.

Это инженерный аргумент разнесения масштабов времени. Разные периоды сами по себе не устанавливают условия применимости теории сингулярных возмущений: нужны свойства объекта и оценка времени установления быстрого контура. В работе оно не измерялось отдельно, поэтому раздельный анализ и устойчивость из выбранных периодов не следуют.

## 6. Что не установлено

Раздел обязателен: без него предыдущий выглядит сильнее, чем он есть.

1. **Формального доказательства устойчивости нет.** Функция Ляпунова не построена, сходимость связанной пары контуров не доказана. Объект — нестационарный, частично ненаблюдаемый (`C(t)`), с целочисленным управлением и насыщениями, поэтому классические результаты для линейных стационарных систем неприменимы напрямую.
2. **Коэффициенты подобраны измерением, а не выведены** из свойств системы. Чувствительность измерена и велика: один коэффициент, взятый в десять раз больше нужного, стоил 69% в p95 — больше, чем весь выигрыш от адаптации. Способа вывести значения аналитически в работе нет, и это её главная слабость.
3. **Цель по закону Литтла привязана к внешне заданному SLO** и потому режимозависима: там, где цель заведомо достижима, правило снижает хвост без потерь; там, где цель приближается к физически достижимому минимуму, единственный способ её выполнить — перестать обслуживать, и правило отбрасывает трафик, которого ничто не требовало. Подход, измеряющий очередь относительно **собственного наблюдённого минимума** системы (как Netflix Gradient), этой уязвимости лишён.
4. **Условие разнесения масштабов проверено физическим рассуждением, а не измерением** времени установления быстрого контура.
5. **Стенд — один, машина — одна**, клиент нагрузки живёт в одной JVM с сервером.

## 7. Связь с продолжением работы

Пункт 2 предыдущего раздела — отсутствие принципиального способа выбрать коэффициенты — задаёт естественное продолжение: замена подобранных констант обучаемой политикой. Контур для этого уже пишет журнал троек `(состояние, действие, результат)` в формате JSONL. **Объём накопленных данных на сегодня недостаточен** для обучения, и порождены они детерминированной политикой без разброса действий, поэтому для обучения потребуется отдельный сбор с исследующей политикой. В настоящей работе интеллектуальная адаптация не рассматривается.
